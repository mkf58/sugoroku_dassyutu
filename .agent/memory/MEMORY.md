# MEMORY

## プロジェクト概要
- タイトル（仮）：すごろく×魔女の館脱出 (Sacrifice & Dice in the Witch's Mansion)
- エンジン・言語：Godot Engine 4 (GDScript)
- ターゲット：PC (Steam / itch.io)
- ジャンル：ターン制すごろく脱出ホラーADV
- 開発方針：テスト駆動型ウォーターフォール開発（TDD-WF）

## 学習した知識・教訓
1. **ホラー作品の演出トーン：**
   - お涙頂戴や感傷的な演出を徹底して排し、冷徹に儀式を執行する乾いた質感を維持する。
   - CERO:C / PG-12相当を遵守し、ゴア演出は暗転・フォーリー音響（陶器破壊音等）で代替表現する。
   - 分岐選択肢を露骨に表示すると隠し要素がネタバレするため、条件達成時のみシームレスに特殊イベント（説得・逆走）を発生させる。
2. **ゲームシステム設計とバグ防止原則：**
   - 味方ユニット（主人公・少女）の操作コマンドは共通化（1.ダイス移動 / 2.アイテム使用 / 3.魔法使用 / 4.待機・祈る ＋ コマンド閉じる）し、状態遷移の複雑化とバグを防ぐ。
   - 魔法使用時は移動不可（移動と魔法の二者択一）とし、明快なボードゲーム的駆け引きを作る（※MPや魔力といった数値コストは存在せず、1ターン1回行動制限）。
   - 土魔術の地中潜行中は「祈る」コマンド選択で潜行状態をそのまま継続できる。
3. **マス種別と状態管理の抽象化・シンプル化：**
   - イベント系マス（宝箱、石碑、痕跡、解放、介錯）は個別CellTypeに細分化せず、`EVENT` マス（＋`event_id`）に一元化する。
   - 階段（フロア遷移）と脱出（クリア）は本質的に同一であるため、`EXIT` マスとして統合する。
   - 特殊停止マス（+2マス、もう1回、振り出し）は停止時にシグナルを連鎖発動させ、追加移動権やダイス再ロールへ即時移行させる。
4. **リアルタイム判定とAI制御：**
   - 捕縛・水トラップ判定はターン終了時の一括処理ではなく、**1歩進むごとにリアルタイム判定**する。
   - **魔女も水トラップを踏んだ瞬間即座に停止**し、残歩数破棄で行動終了となる。
   - 魔女の追跡ターゲットは「最短距離の未潜行ユニット」を優先し、同距離時は `主人公 > 炎 > 風 > 水 > 土 > その他`。全員潜行時は初期配置位置へ移動する。
5. **ユーザーストレス軽減・快適性の設計原則：**
   - **未潜行魔女の進入禁止化（理不尽死防止）：** 到達可能マス計算時、未潜行魔女がいるマスを進入禁止障害物として除外することで、ハイライトされた安全なマスを選んだのに移動途中で魔女に捕縛される理不尽を100%防止する。
   - **到達可能マスの1クリック移動：** 手動で中継マスを複数回クリックする仕様は廃止し、出目確定時に折り返し含む全到達マスを一括ハイライトし、目標マスを1クリックするだけで移動するUIが最も快適。
   - **マウスポインタ直下へのダイスボタン展開（ゼロ動線）：** プレイヤーターン開始時や右クリック復帰時、現在マウスポインタがある位置の直下に「🎲 ダイスを振る」ボタンが重なるようポップアップ位置を自動調整することで、マウス移動ゼロですぐにダイスを振れる。
   - **出目確定後のキャンセル不可ルール：** すごろくゲームの根本原則として、一度ダイスを振った（またはアイテム等で出目を確定した）後は出目キャンセルによる振り直しは行わせず、確定移動させる。
   - **カメラ操作：** マウスホイールで0.5〜2.5倍拡大縮小、右クリック長押しドラッグでパン移動（クリックのみならキャンセル発火）がPC向け操作として極めて自然。
   - **UI階層と戻る機構の一元化（`_go_back`）：** モーダル表示中、コマンドメニュー表示中、盤面確認中などの各画面状態において、右クリックおよびEscによる「1つ前の画面への復帰」を一元管理する。
   - **Godot 4のイベント伝播・吸収対策：** モーダル画面（ItemSelectModal等）で右クリック/Escを検知する際は、背景ColorRectやPanelの `MOUSE_FILTER_STOP` によるイベント吸収を回避するため、ルートノードの `_input(event)` で拾って `get_viewport().set_input_as_handled()` する。
   - UI操作は**『左クリック＝すべて確定・選択』『右クリック＝すべてキャンセル・閉じる』**を徹底厳守する。
   - 画面クリックスキップによるTween省略、画面内ログパネル（DebugLogger）および「📋 ログコピー」ボタンによる即時デバッグ環境を担保する。
6. **CI/CDとGitHub Actionsの運用原則：**
   - **無料枠節約設計：** ランナーOSはLinux（`ubuntu-latest`：消費倍率1倍）一択。ブランチへのpushトリガーは統合ブランチ（`dev` / `main`）に限定し、作業中ブランチへのpushでは動かさない。手動検証用に `workflow_dispatch` を配置する。
   - **Godot 4のヘッドレスCI特有の罠（クラスキャッシュ）：** クリーン環境では `.godot/global_script_class_cache.cfg` が未生成のため `class_name` が未認識となる。テスト前に `godot --headless --path <dir> --editor --quit || true` でプロジェクトを初期化し、テストランナー側でも `preload` を併用することで確実に解決する。
   - **ブランチ保護ルール（Required Status Checks）：** PR運用を行う実務現場では、PR作成トリガー（`pull_request`）とブランチ保護ルールを組み合わせることで、「テスト失敗時はマージボタンを物理的にブロック」する品質ゲートウェイを構築できる。
7. **ドキュメント管理ルール：**
   - 基本設計書は、実装後の結合テスト仕様書へそのまま転用できるよう、表形式の結合テスト観点（IT-UI, IT-TRN, IT-DAT）を必ず含めて記述する。
   - QAのログは必ず `.spec/PLAN.md` に残し、決定事項を速やかに要件定義書および基本設計書に反映する。
